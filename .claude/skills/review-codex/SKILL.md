# Codex実装レビュー

`code_review.md`の「コードレビューの進め方（実装完了後）」を実行するためのスキル。Codexが実装を完了しレビュー依頼があったときに使う。GitHub PRは使わず、Markdownファイルでレビューのやり取りを記録する。

## 前提ドキュメント

レビューを始める前に、**必ず**以下を確認する（すでに読んでいれば読み直さなくてよい）。

- `code_review.md`（**必読**。「コードレビュー基準」「コードレビューの進め方」の詳細がここにまとまっている）
- `AGENTS.md`（特に「7. アーキテクチャ上、常に守るべき制約」「10. AIに実行してほしくないコマンド・操作」）
- `code_style.md`（コーディング規約）
- `design.md`（API定義・ディレクトリ構成・データ設計）
- `requirements.md`（機能要件・エラーハンドリング要件）

## 手順

1. **対象タスクの特定**
   - ユーザーからタスクID（例: `T2-1`）の指定があればそれを使う。指定がなければ`docs/reviews/`配下で最新の`*_impl.md`を探す
   - `docs/reviews/T{フェーズ}-{連番}_impl.md`を読み、実装内容・変更ファイル一覧・設計判断で迷った点・動作確認方法を把握する

2. **差分の確認**
   - 該当する機能ブランチと`develop`の`git diff`を取得する（例: `git diff develop...<機能ブランチ名>`）
   - **レビューの本体はこの差分に基づいて行う**。impl.mdは意図・背景を理解するための補助情報として扱い、差分に書かれていない変更点も見逃さないようにする

3. **レビュー観点**（`code_review.md`「コードレビュー基準」に準拠）
   - `design.md`のAPIエンドポイント定義・ディレクトリ構成・データ設計と一致しているか
   - `AGENTS.md` 7章「アーキテクチャ上、常に守るべき制約」からの逸脱がないか（Tauri/FastAPI間の通信方式、Ollama以外への外部通信、ファイル操作のパストラバーサル対策、確認モード/自走モードのゲートなど）
   - `code_style.md`に沿っているか（`any`型の使用、制御構文のネスト、型ヒント、ディレクトリ責務分離など）
   - `requirements.md`のエラーハンドリング要件を満たしているか
   - `AGENTS.md` 10章「AIに実行してほしくないコマンド・操作」に抵触する操作が含まれていないか
   - `implementation_plan.md`のタスク粒度・依存関係を守った差分になっているか

4. **レビュー結果の記録**
   - `docs/reviews/T{フェーズ}-{連番}_review.md`を作成する
   - 記載内容:
     - 指摘事項（重大度がわかる形で列挙。問題なければ「指摘なし」と明記）
     - 承認可否: `承認` または `要修正`
     - 上記レビュー観点に照らした所見
   - ディレクトリ`docs/reviews/`が存在しない場合は作成する

5. **結果の伝達**
   - `要修正`の場合は、レビューmdの指摘事項をユーザー（またはCodex）にわかりやすく要約して伝える
   - `承認`の場合は、`AGENTS.md` 3章の連携フローに従って`develop`へのマージを進めてよい旨を伝える

## 注意事項

- レビューはコメントで終わらせず、必ず`docs/reviews/T{フェーズ}-{連番}_review.md`というファイルとして残すこと（GitHub PRを使わない代わりの記録手段のため）
- 同じタスクIDで再レビューする場合は、既存の`_review.md`を上書きせず、対応内容と再レビュー結果を追記する
- レビュー対象はコード全般だが、特にセキュリティ（パストラバーサル、外部通信の混入）と、AGENTS.md 10章の禁止コマンドへの抵触は重点的に確認する
