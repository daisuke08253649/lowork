# コードレビュー

> `AGENTS.md`から参照される詳細ドキュメント。「レビュー基準（何を見るか）」と「レビューの進め方（どう回すか）」をまとめている。Codexはレビュー時に、Claude Codeは実装・修正時にここを参照すること。

---

## コードレビュー基準（Codex向け）

差分レビュー時に以下を確認する。`AGENTS.md`末尾の「Review guidelines」は、この基準をCodex向けに要約したもの。

- `design.md`のAPIエンドポイント定義・ディレクトリ構成・データ設計と一致しているか
- `AGENTS.md`「アーキテクチャ上、常に守るべき制約」からの逸脱がないか
- `code_style.md`に沿っているか（型ヒント、ディレクトリ責務分離など）
- `requirements.md`のエラーハンドリング要件（Ollama未起動時にUI上でわかりやすく表示、など）を満たしているか
- 新規の外部通信（分析ツール、外部API呼び出しなど）が紛れ込んでいないか（完全ローカル動作の要件違反）
- ファイル書き込み・削除処理に想定外の副作用がないか（プロジェクトフォルダ外への書き込み、確認モードのスキップなど）
- `implementation_plan.md`のタスク粒度・依存関係を守った差分になっているか（1タスクの範囲を大きく超えていないか）

## コードレビューの進め方（GitHub PR）

`AGENTS.md`「連携フロー」を具体化したもの。レビューは`develop`を向いたGitHubのPR上でCodexが行い、やり取りはPRのコメントとして記録する。

### レビューを依頼するタイミング

Claude Codeは、次のタイミングで**必ず**PRに`@codex review`とコメントする。

- `develop`を向いたPRを作成したとき
- Codexの指摘などを受けてPRを修正し、コミット＆pushしたとき

```bash
gh pr comment <PR番号> --body "@codex review"
```

> Codex側の自動レビューが有効になっている場合も、依頼漏れを防ぐため`@codex review`のコメントは省略しない。

### 手順

1. Claude Codeは実装が完了したら機能ブランチをpushし、`develop`を向いたPRを作成する（`gh pr create --base develop`）
   - PRタイトル: `T{フェーズ}-{連番}: 内容`（Issue対応の場合は対象のIssue番号も入れる）
   - PR本文に書く内容: 実装したタスクID・Issue番号と概要、変更したファイル、設計判断で迷った点・独自に判断した点、確認結果（Lint・ビルド・動作確認）、開発者に手動で確認してほしい項目
   - Issueに対応するPRは、本文に`Refs #番号`を書いてIssueと関連付ける。リポジトリのデフォルトブランチは`main`なので、`develop`向けのPRに`Closes #番号`を書いてもIssueは自動でクローズされない
2. PRを作成したら、PRに`@codex review`とコメントする
3. Codexのレビュー結果（PRのレビューコメント）を確認する
   - 指摘がある場合: Claude Codeが修正してコミット＆pushし、もう一度`@codex review`とコメントする。指摘に対応しない場合は、その理由をPRにコメントで残す
   - 指摘がない場合: 開発者に報告する
4. 開発者の承認を得たら、PRを`develop`にマージする（`gh pr merge <PR番号> --merge`）。マージ後、ローカルの機能ブランチは削除してよい
5. Issueに対応するPRをマージしたら、対応したIssueを手動でクローズする（`gh issue close <Issue番号> --comment "PR #<PR番号> でdevelopにマージしました"`）

> `docs/reviews/`配下のmdファイル（`*_impl.md` / `*_review.md`）は、PRによるレビューに移行する前（T10-2まで）の作業記録として残す。新しいタスクでは作成しない。
