# コードレビュー

> `AGENTS.md`から参照される詳細ドキュメント。「レビュー基準（何を見るか）」と「レビューの進め方（どう回すか）」をまとめている。Claude Codeはレビュー時に、Codexは修正時にここを参照すること。

---

## コードレビュー基準（Claude Code向け）

差分レビュー時に以下を確認する。

- `design.md`のAPIエンドポイント定義・ディレクトリ構成・データ設計と一致しているか
- `AGENTS.md`「アーキテクチャ上、常に守るべき制約」からの逸脱がないか
- `code_style.md`に沿っているか（型ヒント、ディレクトリ責務分離など）
- `requirements.md`のエラーハンドリング要件（Ollama未起動時にUI上でわかりやすく表示、など）を満たしているか
- 新規の外部通信（分析ツール、外部API呼び出しなど）が紛れ込んでいないか（完全ローカル動作の要件違反）
- ファイル書き込み・削除処理に想定外の副作用がないか（プロジェクトフォルダ外への書き込み、確認モードのスキップなど）
- `implementation_plan.md`のタスク粒度・依存関係を守った差分になっているか（1タスクの範囲を大きく超えていないか）

---

## コードレビューの進め方（実装完了後）

`AGENTS.md`「連携フロー」のステップ2〜3を具体化したもの。GitHub PRは使わず、レビューのやり取りを`docs/reviews/`配下のMarkdownファイルとして記録に残す。CodexとClaude Codeは直接連携できないため、各ステップの受け渡しは開発者が行う。Claude Code側はこの手順を`review-codex`スキルとして呼び出せるようにしている（詳細は`SKILL.md`）。

1. Codexはタスクの実装完了後、実装内容をまとめたMarkdownファイルを`docs/reviews/T{フェーズ}-{連番}_impl.md`として保存する（例: `docs/reviews/T2-1_impl.md`）
   - 記載内容: 実装したタスクID・概要、変更したファイル一覧、設計判断で迷った点・独自判断した点、動作確認方法
2. 開発者がClaude Codeに`review-codex`スキルでレビューを依頼する。Claude Codeは、上記の実装サマリーmdと**該当ブランチの`git diff`の両方**を確認してレビューする。サマリーmdは実装の意図・背景を把握するための補助情報として使い、レビュー自体は必ず実際の差分に基づいて行う（サマリーに書かれていない変更の見落としを防ぐため）
3. Claude Codeはレビュー結果を`docs/reviews/T{フェーズ}-{連番}_review.md`として保存する
   - 記載内容: 指摘事項、承認可否（`承認` / `要修正`）、上記「コードレビュー基準」・`AGENTS.md`「アーキテクチャ上、常に守るべき制約」・`code_style.md`に照らした所見
4. `要修正`の場合、開発者がCodexにレビューmdの内容を伝えて修正を依頼する。Codexは修正後、実装サマリーmdに対応内容を追記する。開発者は再度Claude Codeに`review-codex`スキルで再レビューを依頼する
5. `承認`になったら、`AGENTS.md`「連携フロー」に従い機能ブランチを`develop`にマージする

> `docs/reviews/`配下のファイルは作業記録として残す。MVP完成後に整理・アーカイブするかは運用しながら判断する。
