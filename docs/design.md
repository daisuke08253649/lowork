## 1. システムアーキテクチャ

```
[React UI]
    ↕ HTTP (localhost:8000)
[FastAPI sidecar]
    ├── /chat/*        → Ollama API 呼び出し
    ├── /rag/*         → ChromaDB + LangChain
    ├── /files/*       → ファイル読み書き
    └── /projects/*    → プロジェクト管理
[Ollama]               ← FastAPI (LLM推論 + Embedding)
[ChromaDB]             ← FastAPI (プロジェクトごとにcollection分離)
[SQLite]               ← FastAPI (チャット履歴 + プロジェクトメタ)
```

### 設計方針
- React → FastAPI は **直接HTTP**（Tauri IPC経由なし）  
  React側から `http://127.0.0.1:8000` に対して axios でリクエストを送る。Tauri の `invoke()` は使わない
- Tauri の役割はウィンドウ管理・サイドカー起動・終了のみ
- FastAPI は Tauri サイドカーとして起動（アプリ終了時に自動停止）

## 3. データ設計

### 3-1. SQLite テーブル定義

**projects（プロジェクト）**

| カラム | 内容 |
|--------|------|
| id | 一意なID（UUID） |
| name | プロジェクト名 |
| folder_path | 対象フォルダのパス（重複不可） |
| created_at | 作成日時 |

**chat_conversations（チャット会話）**

| カラム | 内容 |
|--------|------|
| id | 一意なID（UUID） |
| project_id | 紐づくプロジェクトID。NULLの場合は普通のチャット |
| title | 会話タイトル（先頭メッセージから自動生成） |
| created_at | 作成日時 |

**chat_messages（チャットメッセージ）**

| カラム | 内容 |
|--------|------|
| id | 一意なID（UUID） |
| conversation_id | 紐づく会話ID |
| role | 送信者（`user` または `assistant`） |
| content | メッセージ本文 |
| created_at | 送信日時 |

### 3-2. ChromaDB 設計

| 項目 | 設定値 |
|------|--------|
| collection名 | `project_{project_id}` |
| Embeddingモデル | `nomic-embed-text`（Ollama API経由） |
| chunk_size | 500 tokens |
| chunk_overlap | 50 tokens |
| 取得件数 (top_k) | 5件 |
| メタデータ | `{file_path, filename, last_modified}` |

## 4. API エンドポイント定義

### チャット

| Method | Path | 概要 |
|--------|------|------|
| POST | `/normal-chat` | 普通のチャット（SSEストリーミング） |
| POST | `/project-chat` | プロジェクトチャット（JSON一括返却） |
| GET | `/chat/conversations` | チャット一覧 |
| GET | `/chat/conversations/{id}/messages` | メッセージ一覧（指定した会話内のAIとのトーク履歴） |
| DELETE | `/chat/conversations/{id}` | チャット削除 |

### プロジェクト

| Method | Path | 概要 |
|--------|------|------|
| GET | `/projects` | プロジェクト一覧 |
| POST | `/projects` | 新規作成（インデックス構築開始） |
| DELETE | `/projects/{id}` | 削除（ChromaDB collectionも削除） |
| GET | `/projects/{id}/files` | ファイルツリー取得 |
| GET | `/projects/{id}/index-status` | インデックス進捗 `{status, progress}` |

### Ollama

| Method | Path | 概要 |
|--------|------|------|
| GET | `/ollama/models` | インストール済みモデル一覧 |
| POST | `/ollama/pull` | モデルDL（SSEで進捗ストリーミング） |
| GET | `/ollama/status` | Ollama起動確認 |
| GET | `/ollama/available-models` | スクレイピング結果＋互換性判定を返す |

### システム

| Method | Path | 概要 |
|--------|------|------|
| GET | `/system/specs` | PCスペック取得（RAM・GPU） |

## 5. プロジェクトチャット処理フロー

```
① ユーザーがメッセージ送信
        ↓
② ChromaDB でRAG検索（top_k=5）
   → 関連チャンクとファイルパスを取得
        ↓
③ Ollama へリクエスト
   System Prompt:
     - 関連ファイルの内容を提示
     - 必ず以下のJSON形式で返答すること（後述）
        ↓
④ JSONパース
        ↓
   ファイル操作あり？
   ├── YES + 確認モード → ⑤a
   ├── YES + 自走モード → ⑤b
   └── NO              → ⑥ チャット表示のみ
        ↓
⑤a 確認モード：ファイル名・全文プレビューを表示
               → ユーザーが「適用」ボタンをクリック → ファイル書き込み
⑤b 自走モード：即座にファイル書き込み
        ↓
⑥ messageをチャットに表示 / ファイルツリーを更新
```

### LLM出力フォーマット（System Promptで指示）

```json
{
  "message": "ユーザーへの返答テキスト",
  "file_op": {
    "action": "create",
    "filename": "example.md",
    "content": "ファイルの全文"
  }
}
```

- `action`: `"create"` | `"edit"`
- `file_op` が不要な場合は `null`
- `edit` の場合、`filename` でプロジェクトフォルダ内を検索して対象ファイルを特定

### 普通のチャット処理フロー

```
① ユーザーがメッセージ送信
        ↓
② Ollama へリクエスト（SSEストリーミング）
        ↓
③ トークンを順次UIに流し込む
        ↓
④ 完了後、SQLiteにメッセージ保存
```

#### 設定画面：モデル一覧の取得ロジック

設定画面を開いたタイミングで `ollama.com/library` をスクレイピングし、モデル一覧を取得する。取得結果はキャッシュして毎回スクレイピングしない。

実装は [frefrik/ollama-models-api](https://github.com/frefrik/ollama-models-api) を参考に自作する。このリポジトリはFastAPIベースで同様のスクレイピングを実装しており、レスポンスに `labels`（例: `["8B", "70B"]`）が含まれるため、互換性判定に必要なパラメータ数をそのまま利用できる。

**互換性判定ロジック**

PCのRAMを `psutil`（Python）で取得し、モデルのパラメータ数から必要メモリを概算（量子化Q4前提）して判定する。

| パラメータ数 | 必要メモリ目安 |
|-------------|--------------|
| 3B以下 | 約3GB |
| 7B | 約5GB |
| 13B | 約8GB |
| 30B | 約20GB |
| 70B | 約40GB |

| 判定 | 条件 | 表示 | 選択 |
|------|------|------|------|
| ダウンロード可能 | 搭載RAM ≥ 必要メモリ × 1.5 | 緑バッジ | 可 |
| 動作が重くなる可能性 | 搭載RAM ≥ 必要メモリ × 1.0 | 黄バッジ | 可 |
| ダウンロード不可 | 搭載RAM < 必要メモリ | 赤バッジ | 不可（グレーアウト） |

## 7. デザイン定義

具体的な色・アニメーション秒数などは実装時にAIへ委ねる。以下の方針のみ設計書で定義する。

- **テーマ**: ライト / ダーク切り替え対応。設定画面のトグルで切り替え
- **カラー**: モノクロベース（アクセントカラーなし）
- **アニメーション**: しつこくない程度に入れる（ボタンホバー、メッセージ出現など）

> フロントエンド実装（Codex担当）では **shadcn MCP** を使用してコンポーネント・ブロックをレジストリから検索・導入する（詳細は`AGENTS.md`「使用プラグイン」参照）  
> UIコンポーネントライブラリは **shadcn/ui**（Tailwind CSS ベース）を使用する

## 8. 実装優先順位（MVP）

| 優先度 | 機能 | 理由 |
|--------|------|------|
| 1 | Tauri + FastAPI サイドカー起動確認 | 全機能の基盤 |
| 2 | Ollama連携（普通のチャット + ストリーミング） | コア体験の確認 |
| 3 | プロジェクト管理 + ChromaDB インデックス構築 | RAGの前提 |
| 4 | プロジェクトチャット（RAG + ファイル操作） | コア価値 |
| 5 | 確認モード / 自走モード切り替え | UX改善 |
| 6 | チャット履歴の保存・復元 | 利便性 |
| 7 | 設定画面（モデルDL） | 補助機能 |

## 8. その他の設計決定事項

| 論点 | 現状 |
|------|------|
| `edit` 時のファイル特定ロジック | RAG検索結果の上位ファイルを対象とする |
