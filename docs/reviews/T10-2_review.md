### 各Issueの修正の妥当性

- **#7 DNSリバインディング**: ミドルウェアは `TrustedHost`（最も外側）→ `CORS` → Origin検証 の順で、正しく重なっている。Hostの照合はポートを除いた部分で行われる（Starletteの実装）ので、`127.0.0.1:8000` / `localhost:1420` からの正規のアクセスは影響を受けない。Originヘッダーのない要求を通しているが、ブラウザはPOST・DELETEで必ずOriginを付ける。リバインディングは Host の検証で止まるため、問題ない。
- **#8 プロンプトインジェクション**: バックアップは `read_bytes` で行うのでバイト単位で正確に残る。ファイルI/Oは `asyncio.to_thread` 経由で実行されている。区切りタグの無害化（`re.sub` で `project-files` に置換）は、入れ子にしても置換後に閉じタグが復元されないことを確認した。
- **#9 CSP**: 本番の挙動をTauriのソースで確認した（下記「軽微1」も参照）。ビルド後の `dist/index.html` にあるインラインのテーマ判定スクリプトは、codegenがハッシュとして `script-src` に追加するので動く。インラインの `<style>` タグはないため、`style-src` にnonceは付かず、`'unsafe-inline'` が有効なまま残る。Base UI や floating-ui が使う style 属性も阻害されない。

## 軽微（マージを妨げない）

### 軽微1: macOSのデスクトップ開発では `devCsp` が適用されない

Tauri 2.11.5 で開発サーバーをプロキシしてCSPを挿入するのはモバイル開発時だけ（`protocol/tauri.rs` の `#[cfg(all(dev, mobile))]`）。デスクトップ開発では WebView が `http://localhost:1420` を直接開くため、`devCsp` は効かない。

- 実害はない（開発時にCSPがないだけで、本番の `csp` は適用される）
- ただし、`design.md` 8章と `T10-2_impl.md` の「開発用（Vite・HMR用）CSP」という書き方は誤解を招く。また、impl.md の手動確認項目「`npm run tauri dev` でCSPの影響を確認」では、**CSPの影響は確かめられない**。本番CSPの確認は `npm run tauri build` で作ったアプリを起動して行う必要がある
- 対応案: 手動確認項目を `tauri build` 後の起動確認に差し替え、`design.md` に「devCspはモバイル開発時のみ有効」と補足する

### 軽微2: 「元に戻す」は直前の1回分だけで、ディスク上のバックアップを戻すUIはない

`previous_content` は画面の通知の状態にしか残らない。次のメッセージを送ったり画面を移動したりすると、ボタンからは戻せなくなる。ディスクにはバックアップが残るが、復元は手作業になる。同じ攻撃で連続して上書きされた場合、2回目以降の `previous_content` はすでに改ざんされた内容になる（再攻撃で実際に確認）。元の内容は最初のバックアップにある。MVPとしてはこれで許容し、運用でバックアップの場所を知っておけばよい。

### 軽微3: バックアップの保存期間に上限がない

編集のたびに全文が保存され、削除されない。`DELETE /projects/{id}` でも消えない。`design.md` 8章に「MVPでは自動削除しない」と明記されているので、設計どおりではある。容量が問題になった時点で整理機能を検討する。

### 軽微4: 範囲が広すぎるフォルダの判定はルート・ホーム・ホームの上位階層だけ

`/Volumes/<外部ディスク>` のルートや `/Applications` などは登録できる。また、修正前に登録済みのプロジェクトはもう一度検証されない。#7 の本質であるリバインディングは Host 検証で止まっているので、これは被害を広げにくくするための補助策として十分。

### 軽微5: プロンプトの強化は小型モデルでは効果がない（残存リスク）

実測では、`gemma4:e4b` が同じ攻撃に3回とも従った。自走モードでの改ざんそのものは防げておらず、防げているのは「元に戻せない」状態までである。Issue #8 の対応案2（自走モードの即時書き込みを、ユーザーが指定したファイルに限る）は自走モードの仕様変更になるため、開発者が判断するまで保留とした。この判断は妥当。#8 をクローズする場合は、残存リスクとしてIssueに記録しておくこと。
