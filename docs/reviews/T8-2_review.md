### 指摘事項

#### 要修正1: エラーメッセージが画面に一度も表示されない

進捗パネルは `{pullState.status}`（`Settings.tsx:291`）しか描画していない。一方、
ダウンロード開始失敗時の catch（`Settings.tsx:187`）と、終端イベントを受け取れなかった場合
（`Settings.tsx:202`）は **`error` だけを設定し `status` を更新しない**。
`pullState.error` は文字色を赤にする条件（`Settings.tsx:291`付近の`cn`）にしか使われていないため、
エラー文言はどこにも出ない。

実測（すべて画面上の文字列）:

| シナリオ | バックエンドの応答 | 画面表示 |
|---|---|---|
| Ollama停止 | 503 `{"detail":"Ollamaに接続できません"}` | 赤字で「ダウンロードを開始しています」 |
| 上流404 | 502 `{"detail":"モデルのダウンロードを開始できません"}` | 赤字で「ダウンロードを開始しています」 |
| 上流500 | 502 同上 | 赤字で「ダウンロードを開始しています」 |
| successを送らずに切断 | （SSEは正常終了） | 赤字で「pulling aabbcc」／40%のまま |

`requirements.md`「Ollamaが起動していない場合はUI上にわかりやすいエラーを表示する」を満たしていない。
ユーザーには「開始しています」と出たまま止まって見える。

対応案: catch節と`!receivedTerminalEvent`節でも `status` を同じ文言に更新するか、
パネル側を `{pullState.error ?? pullState.status}` に変える。

> 補足: SSEストリーム**中**の `{"error": ...}` イベントは `status` にも代入されるため正しく表示される
> （上流のモデル不在、不正JSON、突然切断の3ケースを実測して確認済み）。表示されないのは上記4経路のみ。

#### 要修正2: バックエンドの`detail`を取得できておらず、2つのメッセージが実質入れ替わっている

`streamOllamaPull`は`responseType: "stream"`で送っているため、エラー時の
`error.response.data` は **`ReadableStream`** になる（実測: `Object.prototype.toString` →
`[object ReadableStream]`、`instanceof ReadableStream` → `true`）。
そのため `apiErrorSchema.safeParse(error.response?.data)`（`ollama.ts:106`）は常に失敗し、
`apiErrorSchema` は死にコードになっている。

結果、`getStreamErrorMessage` のフォールバックだけが効き、意味が逆転する:

| 実際に落ちているもの | axiosの状態 | 返る文言 | 正しい文言 |
|---|---|---|---|
| Ollama（バックエンドは生存） | 503、`response`あり | モデルのダウンロードを開始できません | Ollamaに接続できません |
| バックエンド | `ERR_NETWORK`、`response`なし | Ollamaに接続できません | （バックエンド未起動の旨） |

いずれも実測で確認した（後者は死んでいるポートへ同条件でPOSTして`hasResponse:false`を確認）。
要修正1を直しても、この状態では誤ったメッセージが表示される。両方あわせて修正が必要。

対応案: エラー時のみ `await error.response.data` をテキストとして読み出してから`apiErrorSchema`にかけるか、
`validateStatus`を使って先にステータスを判定し、エラーレスポンスは`responseType`を変えて取り直す。
あわせて、`await`を一切行っていない `getStreamErrorMessage` / `toPullError` の `async` も外せる。

#### 要修正3: 進捗率が200%になる。多レイヤーでは0%へ何度も巻き戻る

`completed: event.completed ?? currentState.completed`（`Settings.tsx:175`）が、
**前のレイヤーの`completed`を次のレイヤーへ持ち越す**。Ollamaは新しいレイヤーの開始時に
`total`だけを送り`completed`を送らないことがあるため、`completed`（前レイヤーの完了サイズ）÷
`total`（新レイヤーのサイズ）という無関係な割り算になる。

実測（レイヤー1: total=1000/completed=1000 → レイヤー2: total=500のみ）:

```
llama3.1:8b | 100% | pulling layer1   aria-valuenow=100  width:100%
llama3.1:8b | 200% | pulling layer2   aria-valuenow=200  width:200%   ← 破綻
llama3.1:8b | 100% | pulling layer2   aria-valuenow=100  width:100%
```

`aria-valuemax="100"` に対して `aria-valuenow="200"` となり、ARIA的にも不正。バーはトラックを溢れる。

また`total`/`completed`はレイヤーごとの値であり全体の進捗ではないため、
レイヤーが複数あると 50%→100%→50%→100%→50%→100% と往復する（3レイヤーで実測）。
実モデルは巨大なblobとごく小さいlicense/templateなどが混在するので、実運用でも必ず起きる。

対応案: `digest`が変わったら`completed`/`total`をセットで捨てる（最低限200%は防げる）。
可能なら`digest`ごとの`completed`/`total`を保持して合算する。

#### 要修正4: ダウンロード完了後も全ボタンが無効のまま、当該行は「ダウンロード中」のまま

`disabled={isUnavailable || pullState !== null}`（`Settings.tsx:103`）と
`{isPulling ? "ダウンロード中" : "ダウンロード"}`（`Settings.tsx:109`）は、
どちらも「pullが終わったか」ではなく「パネルが残っているか」で判定している。
`pullState`は`success`受信後も`完了`を押すまで残るため:

- 実測: success表示後の時点で **640ボタン中、有効なものは0**（ダウンロード可能な313行も全て無効）
- 実測: ダウンロードし終えた `llama3.1:8b` のボタンラベルは **「ダウンロード中」**

完了しているのに「ダウンロード中」と表示するのは誤情報で、かつ`完了`に気付かないと一覧全体が固まったままになる。

対応案: 完了・エラー状態を`isPulling`/`disabled`の条件から除く（例: `pullState`に
`isFinished`相当を持たせ、進行中のときだけ無効化する）。

### 要修正1: ダウンロード完了後・エラー後、ボタンは押せるのに何も起こらない（修正による退行）

`disabled`の条件は `isUnavailable || isDownloadInProgress`（`Settings.tsx:120`）に変わり、
ラベルも `isPulling && isDownloadInProgress`（`:126`）になった。ここまでは意図どおり。
しかし `handlePull` 冒頭のガードは **`if (pullState) { return; }` のまま**（`Settings.tsx:173`）で、
`isInProgress`を見ていない。`pullState`は`完了`／`閉じる`を押すまで残るため、
**有効に見えるボタンを押しても即座にreturnして何も起きない**。

実測（`llama3.1:8b`のダウンロード成功直後、パネルを閉じずに`mistral:7b`をクリック）:

| 項目 | 実測値 |
|---|---|
| ボタンの状態 | `disabled: false` / ラベル「ダウンロード」 |
| 上流Ollamaへのpull | **0件**（スタブのログに記録なし） |
| バックエンドへのリクエスト | **0件** |
| 進捗パネル | `llama3.1:8b`「ダウンロードが完了しました」のまま変化なし |

エラーパネル表示中も同じ（`mistral:7b`をクリック → パネルは`llama3.1:8b`のエラーのまま）。

第1回時点の挙動（ボタンが無効でグレーアウト）は不親切ではあったが「押せない」ことは伝わっていた。
今回は押せる見た目のまま無反応になったため、**ユーザーから見た分かりにくさはむしろ悪化している**。

対応案: ガードを `if (pullState?.isInProgress) { return; }` に変え、
新しいpullの開始時に`setPullState`で既存パネルを上書きする（`:178`の`setPullState`がそのまま新状態に置き換わる）。

`canDismissPull = pullState !== null && !pullState.isInProgress`（`Settings.tsx:272`）のため、

#### 軽微3: 実際のダウンロード中は英語表示のまま（部分対応）

`formatPullStatus`（`Settings.tsx:58-67`）が変換するのは
`success` / `pulling manifest` / `verifying sha256 digest` / `writing manifest` /
`removing any unused layers` の5つのみ。

実測でも「pulling l1」「pulling layer2」がそのまま表示された。
所要時間の大半を占める表示が英語のままなので、`pulling `で始まる場合の扱いを足すと効果が大きい。

#### 軽微4: 進捗が一時的に後退する（仕様確認）

digestごとに`completed`/`total`を保持して合算する方式のため、

第1回で指摘した200%とレイヤーごとの0%全戻りは解消されており（`aria-valuenow`は常に
`aria-valuemax`=100以下、全シナリオで確認）、実Ollamaはレイヤーを早い段階でまとめて通知するため
実害は限定的。修正は必須ではないが、承知の上の挙動として記録しておく。

#### 軽微5: `design.md`に表示ルールの変更が反映されていない

`visibleVariants`（`Settings.tsx:69-72`）で、サイズが1つのモデルは素の名前のvariantを表示しない

`design.md`6章は「各モデルには、既定タグを使う素のモデル名のvariantも含める」としか書いておらず、
表示側の新ルールが記録されていない。`git status`上も`design.md`は未変更。

（例: 「サイズが1つのモデルは、素の名前のvariantを一覧に表示しない（対象が同一のため）」）。
