## 中1: `POST /project-chat` に5秒のHTTPタイムアウトが効いており、実用上ほぼ必ず失敗する

`src/api/client.ts` の `apiClient` は全リクエスト共通で `timeout: 5_000` を持つ。
`streamNormalChat()` は `timeout: 0` を明示して解除しているが、**`sendProjectChat()` は指定していない**ため 5 秒でアボートする。

```ts
// src/api/chat.ts:206 — timeout指定なし → apiClientの5秒が適用される
const response = await apiClient.post<unknown>("/project-chat", { ... });

// src/api/chat.ts:256 — 普通のチャットは解除済み
response = await apiClient.post<ReadableStream<Uint8Array>>("/normal-chat", {...}, {
  adapter: "fetch", responseType: "stream", timeout: 0,
});
```

`/project-chat` は「インデックス更新 → 埋め込み検索 → LLMがファイル全文を含むJSONを非ストリーミングで生成」を1リクエストで行う同期APIであり、5秒はまったく足りない。

### 実測

`src/api/client.ts` と同じ設定のaxiosクライアントで実バックエンドを叩いた結果:

| 条件 | 結果 |
|---|---|
| LLM遅延0秒・ファイル1件 | 200 OK（22ms） |
| LLM遅延8秒 | **5,013ms で `ECONNABORTED`** → 画面表示「サーバーに接続できません」 |
| 200ファイル・LLM遅延0秒・埋め込み遅延0秒 | 200 OK だが **3,567ms**（予算の71%をインデックスだけで消費） |
| 500ファイル・LLM遅延0秒・埋め込み遅延0秒 | **5,004ms でタイムアウト** |

500ファイルのケースは**LLMも埋め込みも即答するスタブ**での結果である。実際の `nomic-embed-text` とローカルLLMが動けば、この予算はさらに早く尽きる。

### 実画面で確認した被害（自走モード・LLM遅延8秒）

1. 5秒で「チャットエラー / **サーバーに接続できません**」を表示。実際にはサーバーには接続できているので、メッセージ自体が誤り
2. ユーザーの発言が吹き出しから削除され、入力欄に復元される
3. しかし**サーバー側は処理を完走し、ファイルを書き込む**。`slow_write.md`（内容 `SLOW`）が実際に生成された
4. `shouldRestoreInput` が true のため `setTreeRefreshToken` に到達せず、**ファイルツリーは更新されない**。書き込まれたファイルは次に成功した送信のあとで唐突に出現した
5. 会話もサーバーには保存されるため、**画面の履歴とサーバーの履歴が食い違う**。次の送信でOllamaに渡ったメッセージは `system` + 9往復（18件）だったのに対し、画面上は8往復しか表示されていない。以降、ユーザーに見えないやり取りを踏まえた応答が返る

これは `implementation_plan.md` T6-3 の動作確認項目「『〇〇のメモを作って』→ AIがファイルを生成 → ファイルツリーに反映」が、実LLMでは成立しないことを意味する。また `AGENTS.md` 9章の「自走モードでの即時書き込み」を、ユーザーには失敗と見える状態で行っている点も望ましくない。

### 修正案

```ts
const response = await apiClient.post<unknown>("/project-chat", { ... }, { timeout: 0 });
```

`streamNormalChat` と同じ扱いにするのが最小の修正。ユーザーが待たされ続ける状態を避けたい場合は、`apiClient` の既定値とは別に長めの定数（例: `PROJECT_CHAT_TIMEOUT_MS`）を切るのでもよい。

なお、タイムアウトを延ばしても「送信を中断できない」「サーバー側の書き込みだけ先に進む」構造は残る。中断ボタンやサーバー側のキャンセルはT6-3の範囲外なので今回は求めないが、`file_op` の適用結果が確実に画面に反映されるよう、タイムアウト解除は必須とする。

## 軽微1: インデックス進捗が送信中に表示されない

`FileTree` のポーリングは `status !== "indexing"` になった時点で `clearInterval` され、以後は `projectId` / `refreshToken` が変わるまで再開しない。`refreshToken` が増えるのは**応答受信後**なので、送信中に走る `index_project` の進捗バーは原理的に出ない。

実測: プロジェクトフォルダに150ファイル追加 → 送信 → 1秒後のファイルツリーは進捗バーなし・旧ファイル一覧のまま。応答後に一括で更新された。

その間ユーザーに見えるのは入力欄上の「プロジェクトを検索して応答を生成中...」だけで、何が起きているかわからない。中1を直すと待ち時間が長くなる分、この表示の価値は上がる。送信開始時にも `refreshToken` を1つ進めるだけで進捗バーが出るようになる。

## 軽微2: LLMが空メッセージを返すと空の吹き出しが出る

`{"message": "", "file_op": null}` を返させたところ、中身のない小さな吹き出しが1つ描画された（T6-2 第2回で「サーバー側で空文字が保存される」として挙げた項目が、UIでも可視化された形）。`response.message.trim()` が空なら定型文に差し替えるか、吹き出しを描画しない扱いにするとよい。

## 軽微3: `file_op_error` 表示にファイル名が含まれない

`ProjectChatNotice` は `fileOpError` があると即 return するため、`fileOp.filename` を捨てている。

実測（自走モードで `../outside/evil.md` を返させた場合）:
```
ファイル操作を適用できませんでした
プロジェクトフォルダ内の安全なパスを指定してください
```
どのファイルに失敗したのかがわからない。`fileOp` が非nullなら `${fileOp.filename} を適用できませんでした` とタイトルに含めたい。境界そのものは守られており、`outside/` 側にファイルは作られていないことを確認済み。

## 軽微4: 開発者向けの文言がユーザーに表示される

確認モードで `file_op` があるとき、本文に「**確認モードの適用操作は、次のタスクで追加します。**」と表示される（`src/pages/ProjectChat.tsx:195`）。実装計画上の都合をそのままユーザーに見せている。T7-1で置き換わる前提でも、「適用の操作は準備中です」程度の表現に留めたい。

またタイトルが `auto_memo.md を作成します` と未来形のままで、自走モードでは本文が「適用しました」と過去形になり食い違う。自走モードでは `作成しました` にするのが自然。

## 軽微5: 同一タスク内で連続したEnterで二重送信できる

`sendProjectMessage` の `if (!trimmedMessage || isSending)` はレンダー時のクロージャを見ており、`MessageInput` の `disabled` も再レンダー後にしか効かない。同一タスク内で `keydown` を2回発火させると2件のリクエストが通り、同一メッセージが2回保存された。

```
user '二重送信テスト' / assistant 'default reply'
user '二重送信テスト' / assistant 'default reply'
```

Ollamaに渡った履歴もどちらも18件で、2本が同じ履歴に対して並行実行されている。自走モードなら同じ `create` が2回走り、片方が409になるか、`edit` 同士が同一ファイルを奪い合う。

ただし10ms / 20ms / 40ms 間隔での発火では1件しか通らず（20ms以降は `disabled` も間に合っている）、**人間の連打では再現しなかった**。緊急度は低いが、`isSending` を `useRef` にするか送信中フラグを同期的に立てれば消える。

## 軽微6: プロジェクト会話が履歴に出ず、画面を離れると復元も削除もできない

`list_conversations(None)` は `project_id IS NULL` で絞るため、サイドバーの「チャット履歴」にプロジェクト会話は出ない（実測: 普通のチャット1件のみ）。一方 `useProjectChat` はアンマウントで状態を捨てるので、プロジェクト一覧を経由して戻ると会話は消える。実測でも8往復の会話が空状態に戻った。

サーバー側には会話が残り続け（`GET /chat/conversations?project_id=...` で確認）、UIからは参照も削除もできない。さらに新規会話ごとに `schedule_title_generation` が走るため、誰にも表示されないタイトルを生成するLLM呼び出しが積み上がる。

`design.md` のプロジェクトチャット画面の図にも左サイドバーに「チャット履歴」が描かれているので、どこかで扱いを決める必要がある。T6-3の作業内容には履歴復元が挙がっていないため今回は指摘に留めるが、実装計画書側に扱いを追記しておきたい。

## 軽微7: `useProjectChat` のプロジェクト切替リセットが in-flight レスポンスを無効化していない（潜在）

```ts
useEffect(() => { setConversationId(null); setMessages([]); ... }, [projectId]);
```

送信中に `projectId` だけが変わると、状態はクリアされる一方で進行中のリクエストは生き残り、解決時に**前のプロジェクトの会話IDとメッセージを新しいプロジェクトの状態に書き込む**。その後の送信は `project_id` と `conversation_id` の組が一致せず404になる。

ただし現在のルーティングではプロジェクト間の直接遷移が存在せず（必ず `/projects` を挟むため `ProjectChat` がアンマウントされる）、**この経路は到達不能**であることを実測で確認した（ProjB送信中にProjAへ移動 → ProjAにProjBの応答は出ない）。到達不能なので今回は修正必須としないが、`loadModels` と同じく `isActive` フラグで応答を破棄しておくと安全。

## 新規の軽微指摘

### 軽微A（新規・任意）: Ollamaがストールすると画面が無期限に固まる

`timeout: 0` にした結果、フロント側にタイムアウトがなくなった。バックエンドの `request_project_chat_from_ollama` も `httpx.Timeout(..., read=None, ...)` で**読み取りタイムアウトが無効**（`backend/api/chat.py:185`）なので、上流から下流まで一切の時間上限がない。

「Ollamaが接続は受け付けるが応答を返さない」状態を再現して確認した結果:

- **105秒以上経過しても**「プロジェクトを検索して応答を生成中...」のまま
- 入力欄は無効、エラー表示なし
- **中止・キャンセルに相当するボタンは画面上に存在しない**（ボタン一覧を走査して確認）

つまりユーザーはアプリを再読み込みする以外に抜ける手段がない。なお **Ollamaのプロセスが落ちた場合は正しく復帰する**（ソケットが閉じて 503 →「Ollamaに接続できません」＋入力復元）ことも確認済みなので、問題になるのは「生きているが応答しない」ケースに限られる。

大きなモデルのロードで数分待つのは正常な動作でもあるため、T6-3の範囲で中止ボタンまで作る必要はない。ただし `timeout: 0`（無限）ではなく、十分に長い有限値（例: 10分）を `PROJECT_CHAT_TIMEOUT_MS` として置いておくと、最悪でも操作不能から自動的に復帰できる。バックエンド側の `read=None` も合わせて見直す価値がある。**任意対応**とする。

### 軽微B（新規・任意）: 空応答の差し替えが表示だけで、履歴には空文字が残る

`response.message.trim() || "応答を受け取りました。"` は画面表示の置き換えであり、サーバーに保存されるのは元の空文字（実測で `assistant: '   '`）。次のターンでOllamaに渡る履歴にはこの空メッセージが含まれるため、画面とモデルが見ているものがわずかにずれる。

空応答自体がまれなので実害は小さい。根本的にはバックエンド側（`parse_project_chat_output`）で空メッセージを定型文に寄せるのが筋で、これはT6-2の残課題として既に挙がっている項目と同じ。**任意対応**とする。
