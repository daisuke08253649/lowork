# T9-1 実行サマリー（統合動作確認）

> `implementation_plan.md` の最終確認タスク T9-1 を、Codexの代わりにClaude Codeが実行した記録。
> 初回の統合動作確認ではコード変更を行わず、検出した不具合を `T9-1_review.md` にまとめた。後続のレビュー対応で、同ファイルに記載する修正を実装している。

## レビュー対応（第1回）

- `/ollama/models`は、Ollamaが返す`capabilities`に`completion`を含むモデルだけを返すようにし、Embedding専用モデルがチャットの既定選択になることを防いだ。能力情報を返さない旧形式のOllamaとは引き続き互換性を保つ。
- 選択したチャットモデルをZustandの永続ストアへ保存し、通常チャット・プロジェクトチャット・画面遷移間で共有するようにした。
- Ollamaの上流エラー本文をそのままUIへ渡さず、日本語の定型エラーに正規化した。
- `/project-chat`からのインデックス更新では失敗を呼び出し元へ再送出し、消失したプロジェクトフォルダの古いRAGインデックスで応答を続けないようにした。

### 追加の確認

- Embedding専用（`capabilities: ["embedding"]`）モデルをチャット候補から除外し、`completion`対応モデルと能力情報がない旧形式モデルを候補に残すことを確認した。
- 存在しないフォルダで`index_project(..., raise_on_error=True)`を実行すると、`FileNotFoundError`が呼び出し元まで伝播することを確認した。
- `npm run lint`（既存warning 1件のみ）、`npm run build`、`ruff check backend`、`black --check backend`、`git diff --check`を実行した。

## 要件整合の対応

- プロジェクトチャットの会話履歴について、MVPでも復元を提供する方針を採用した。プロジェクト画面では、そのプロジェクトに紐づく会話だけを共通サイドバーに表示し、会話を選択するとURLの`conversation`指定を通じて保存済みメッセージを読み込む。
- プロジェクト履歴のメッセージ取得には`project_id`も渡し、URLを直接編集して別プロジェクトや通常チャットの会話IDを指定しても復元できないようにした。

## レビュー対応（第2回）

- プロジェクト会話の送信完了後にサイドバーの一覧を再取得し、新しい会話を即座に表示するようにした。初回会話ではタイトル生成完了までポーリングし、タイトルの更新も反映する。
- プロジェクト会話一覧の取得失敗を捕捉し、「チャット履歴の取得に失敗しました」とサイドバーに表示するようにした。
- 会話切替時にもプレビュー・適用済み通知・ファイル操作エラーを初期化し、別会話の提案を誤って適用できないようにした。
- モデル選択をアプリ全体で共有・永続する設計判断を`design.md`へ記録した。

## レビュー対応（第3回・軽微改善）

- プロジェクトチャットの送信成功時、返却された会話IDをURLの`conversation`へ置換設定するようにした。新規作成・既存会話への追記のいずれでも、サイドバーの選択状態とURL復元の対象を現在の会話へ揃える。

## レビュー対応（第3回・残る軽微改善）

- Ollamaの代表的な上流エラー（モデル未検出・チャット非対応・メモリ不足）を、利用者が対処できる日本語メッセージに変換した。
- 同一プロジェクトで新しい会話を始めるボタンを追加した。
- タイトル生成結果がプロンプトのエコーや番号付きの指示文である場合は保存せず、既定タイトルを維持するようにした。
- Ollamaの接続復帰を共有状態として扱い、モデル一覧・プロジェクト会話一覧・ファイルツリーを自動再取得するようにした。
- プロジェクト会話タイトルの更新確認をサイドバー側の単一ポーリングへ統合し、重複する一覧取得を解消した。
- プロジェクト画面を直接開いた場合もプロジェクト一覧を読み込み、見出しにプロジェクト名を表示するようにした。

## レビュー対応（第4回）

- 新規プロジェクト会話の送信後にURLを現在の会話IDへ同期しても、同じ会話を再読込・初期化しないようにした。確認モードのファイル操作提案と自走モードの通知を保持する。
- 会話タイトルは検証前に20文字へ切り詰め、長い生成結果を既定タイトルのまま破棄しないようにした。
- プロジェクト会話一覧のタイトル更新ポーリングに24回の上限を設け、タイトル生成に失敗しても無期限に再取得し続けないようにした。

## チェックリスト以外に実施した確認

- **ファイル操作の安全性（12ケース）**: `../escape.md` / 深いトラバーサル / 絶対パス / サブフォルダ新規作成 / 非対応拡張子 / dotfile / 既存ファイルへのcreate / プロジェクト外へのedit / 存在しないファイルのedit / 不明プロジェクト / 不正action — すべて期待どおり拒否またはエラー。プロジェクト外に1バイトも書き込まれていないことをファイルシステムで確認
- **シンボリックリンク経由の脱出（3ケース）**: ファイルリンク・ディレクトリリンク経由のedit/create をすべて拒否。リンク先の内容は不変。ファイルツリーにもリンクは出ない
- **CORS境界（4ケース）**: 別オリジンからのプリフライトは400、`text/plain` / `x-www-form-urlencoded` の単純POSTは422で弾かれ、ファイル書き込みは発生しない
- **削除系**: 会話削除（会話＋メッセージが消え、サイドバー更新）、プロジェクト削除（DB行削除・Chromaコレクション削除・実ファイルは保持・紐づく会話とメッセージがCASCADE削除、孤児レコード0件）
- **重複プロジェクト作成**: 同一フォルダで409「このフォルダはすでにプロジェクトに登録されています」
- **プロジェクトフォルダ消失時の挙動**: フォルダをリネームした状態での各API（→レビューmdの指摘3）
- **静的チェック**: `npm run build`（tscエラー0・ビルド成功）、`npm run lint`（error 0 / warning 1・既存）、`npm run format:check`（pass）
- **ログ**: バックエンドの想定外例外0件（記録された2件のTracebackはフォルダ消失テストで意図的に発生させたもの）。ブラウザのコンソールエラー0件
