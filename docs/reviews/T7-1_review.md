## 指摘事項

### 軽微1: 「適用する」に同期的な再入防止ガードがない（対応推奨）

`src/pages/ProjectChat.tsx:100-117` の `handleApplyFileOperation` には `isApplying` を同期的に見るガードがない。ガードは `<Button disabled={isApplying}>`（`src/components/project/DiffPreview.tsx:62`）だけで、これは再レンダリング後にしか効かない。**T6-3 軽微5 で `useProjectChat` に `isSendingRef` を入れたのとまったく同じ論点**が、同じ画面の別フローで再発している。

同一タスク内で3回ディスパッチしたときの実測:

| 指標 | 値 |
|---|---|
| 送出された `POST /files/apply` | 3件 |
| サーバー応答 | 204 × 1、409 × 2 |
| ファイル | `new-note.md` は**正しく作成された** |
| 画面表示 | 「同名のファイルがすでに存在します」（赤字） |

つまり**適用は成功しているのにユーザーには失敗と見える**。

さらに悪いのが後続の状態で、成功パスは `setPreviewFileOperation(null)` でモーダルを閉じるため `onClose` を通らず、`fileOperationError` がクリアされない。結果:

- コンポーザーに「チャットエラー / 同名のファイルがすでに存在します」が**居座り続ける**（次の送信でも `setError(null)` しか走らないため消えない）
- **次の別ファイルの提案モーダルを開いた時点で、そのモーダル内にこの古いエラーが表示される**（`dbl.md` の新規提案が、開いた瞬間から「同名のファイルがすでに存在します」を表示した状態で出てくることを確認）

**到達性について（軽微に留めた理由）**: 実際のダブルクリック（1件）、フォーカスした「適用する」上での Enter 8連打（1件）では**再現しなかった**。React は discrete イベントで同期的にフラッシュするため `disabled` が間に合う。再現したのは同一タスク内で `click()` を連続ディスパッチした場合のみ。

**対応案**: `isApplyingRef` を最初の `await` より前に同期的に立てる。あわせて `fileOperationError` を「新しい提案を開いたとき」「新しいメッセージを送ったとき」にもクリアする。

### 軽微2: ファイル操作エラーが「チャットエラー」として二重表示される（対応推奨）

`src/pages/ProjectChat.tsx:120` の

```ts
const displayedError = modelError ?? error ?? fileOperationError;
```

により、`fileOperationError` はモーダル内（`DiffPreview` の `error`）と**コンポーザー上部の Alert の両方**に出る。しかも Alert のタイトルは「チャットエラー」で、ファイル操作の失敗をチャットの失敗として提示してしまう。

実測（400 / 404 / 接続不可のいずれでも再現）:

```
モーダル内:     編集対象のファイルが見つかりません
コンポーザー:   ⚠ チャットエラー
                編集対象のファイルが見つかりません
```

**対応案**: `fileOperationError` は `displayedError` から外し、モーダル内のみで扱う。コンポーザーにも出すならタイトルを「ファイル操作エラー」に分ける。

### 軽微3: 適用成功時のフィードバックがない

適用が成功すると、モーダルが閉じ、通知アラートも `clearNotice()` で消え、**成功を伝えるものが何も残らない**。`create` はファイルツリーに新しい名前が現れるので気づけるが、`edit` はツリーの表示（ファイル名の一覧）が変わらないため**完全に無反応に見える**。`existing.md` の編集で実測。

**対応案**: 「◯◯ を作成／編集しました」を通知アラートに差し替えてから閉じる。

---

### 軽微4: キャンセル・Escape で提案が完全に消え、再表示できない

`onClose` は `setPreviewFileOperation(null)` と `clearNotice()` の両方を呼ぶため、モーダルを閉じると**通知アラートごと消える**。モーダルを再度開く手段はどこにもなく、提案されたファイル全文（数百KBになりうる）は失われる。Escape・キャンセルのどちらでも同じ。

計画書の「「キャンセル」クリック → メッセージのみ表示、ファイル操作なし」という記述自体は満たしている（アシスタントの本文メッセージは残る）。ただし誤って Escape を押しただけで内容を取り戻せないのは、確認モードの目的に照らすと惜しい。

**対応案**: `onClose` では `setPreviewFileOperation(null)` のみとし、通知アラートは残す。アラートを押すとモーダルを再表示できるようにするとなお良い（`notice.fileOp` は保持されているので、`setPreviewFileOperation(notice.fileOp)` を呼ぶだけで再現できる）。

### 軽微6: プロジェクト切替時にモーダル関連のローカル state がリセットされない（任意・防御的）

`src/App.tsx:20` のルートは

```tsx
<Route path="/projects/:projectId" element={<ProjectChat />} />
```

で `key` を持たないため、プロジェクトAからBへ遷移しても `ProjectChat` は同じインスタンスのまま再レンダリングされる。`useProjectChat` は `[projectId]` の effect で会話状態をリセットするのに対し、`ProjectChat` 側の `previewFileOperation` / `fileOperationError` / `isApplying` は**どこでもリセットされない**。

理屈の上では「Aの提案を開いたままBへ遷移 → 適用する → Aのファイル内容がBのフォルダに書き込まれる」（`handleApplyFileOperation` は最新の `projectId` と古い `previewFileOperation` を組み合わせる）が成立する。

**ただし、UI操作では到達できなかった**。モーダルの backdrop がサイドバーへのクリックを遮り、フォーカストラップによりキーボードでもサイドバーへ到達できないため、モーダルを開いたままプロジェクトを切り替える手段が現状は存在しない。SPA遷移を強制する試みも、フルリロードになってしまい再現できなかった。

**対応案**: `useEffect(() => { setPreviewFileOperation(null); setFileOperationError(null); }, [projectId])` を足すか、ルートに `key={projectId}` を付ける。将来モーダルの外に閉じる導線（トースト、サイドバーからの遷移許可など）が入った瞬間に顕在化するため、今のうちに塞いでおくのが安全。

## 検証メモ（指摘ではない）

- **モーダルを閉じた後に backdrop がクリックを奪う現象**を検証中に何度か観測したが（`document.elementFromPoint` が `fixed inset-0 bg-black/50` を返し、60秒以上復帰しないケースあり）、これは**検証環境の artifact** だった。ブラウザ自動化中のタブは `document.visibilityState === "hidden"` で `requestAnimationFrame` が2秒間に0回しか発火せず、Base UI の終了アニメーション待ち（`data-ending-style`）が解消しないために起きていた。スクリーンショットを挟んで描画を発生させると即座にアンマウントされ、通常の可視状態では再現しない。実機（Tauriウィンドウ）では問題にならない。
- `src/components/ui/alert-dialog.tsx` は T4-2 で追加された既存コンポーネントで、T7-1 の差分には含まれない。
- `DiffPreview` という名前だが差分は表示せず、適用後の全文のみを出す。これは計画書の「ファイル全文をコードブロックで表示」に忠実な実装であり仕様どおり。ただし `edit` では**現在の内容が見えないまま全文上書きを承認する**ことになる点は、将来の改善候補として記録しておく。
- `applyFileOperation` に `{ timeout: 0 }` を付けた判断は、T6-3 の `sendProjectChat` と揃っていて妥当。ただし T6-3 第2回で挙げた軽微A（サーバーが応答を返さずストールした場合に無期限で固まり、中止手段がない）が `/files/apply` にも同じく当てはまる。有限のタイムアウト値に統一する際は両方まとめて対応するとよい。
- 回帰確認: 自走モードでモーダルが開かないこと、普通のチャット（送信・応答・履歴タイトル生成）が動作すること、`file_op` が `null` の応答でモーダルが開かないことを確認。いずれも問題なし。

### 新規の軽微（任意）

**軽微A: `/files/apply` も `timeout: 0` のため、サーバーがストールすると中止できない**

バックエンドプロセスを `SIGSTOP` で停止させた状態で「適用する」を押すと、**60秒以上「適用中...」のまま**で、キャンセル・適用の両ボタンが disabled、Escape も無効、backdrop で背後の操作も届かない。中止する手段が画面上に存在しない。`SIGCONT` で復帰させると 204 が返り、モーダルが閉じて `stall.md` が作成され、成功通知も正しく出たので**復帰動作自体は正常**。
