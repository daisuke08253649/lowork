# T6-1 実装サマリー

## 実装した内容

- `backend/services/file_ops.py` に、プロジェクトフォルダ直下のファイルを作成・編集するサービスを追加した。
- `POST /files/apply` を追加した。リクエストは `{ project_id, action, filename, content }` で、`action` は `create` / `edit` のみを受け付ける。
- 作成・編集の対象はMarkdown（`.md`）とテキスト（`.txt`）に限定し、インデクサーと同じ除外ディレクトリを対象外にした。
- プロジェクトが存在しない場合は404、同名ファイルの新規作成は409、編集対象がない場合は404を返すようにした。
- 新規作成の `filename` は単一のファイル名に制限する。編集ではプロジェクト配下の相対パスを受け付け、絶対パス・`..`・null byte・OSの上限を超える名前を400で拒否する。
- 既存のシンボリックリンクおよびシンボリックリンクを経由してプロジェクト外を指す編集対象への書き込みを拒否した。

## 変更ファイル

- `backend/services/file_ops.py`
- `backend/api/files.py`
- `backend/main.py`

## 設計判断

- 要件定義書の「新規ファイルはプロジェクトフォルダ直下」と実装計画書の「既存ファイルはフォルダ内から特定」を両立させた。新規作成は直下のみ、編集はプロジェクト配下の相対パスを安全に受け付ける。これに合わせて、矛盾していた `AGENTS.md` の運用制約も更新した。
- ファイルI/Oは同期サービスに集約し、FastAPIルートから `asyncio.to_thread()` で実行することでイベントループをブロックしない。
- 新規作成は排他モード（`x`）、編集は一時ファイルを `os.replace()` する原子的な置換を用いた。

- 検証用プロジェクトは `DELETE /projects/{id}` を通じて削除し、検証用サーバーは停止済み。`/private/tmp/lowork-t6-1-verify.9QHq1e` は検証の作成物として残している。

## レビュー指摘への対応（2026-08-12）

- `..` を明示的に拒否し、相対パスの各コンポーネント・全体長・null byteを検証するようにした。想定外の `ValueError` もJSONの500応答へ変換する。
- 既存ファイルの編集は、解決後のパスがプロジェクト配下にあることを確認してから実行する。
- 新規作成を排他生成へ、編集を原子的な置換へ変更して、競合や途中失敗による破損リスクを抑えた。
- 隔離したネスト済みファイルに対する `edit` が204で成功すること、`filename: ".."` とJSONのnull byteが400で拒否されることをAPI経由で確認した。検証用プロジェクトは削除API経由で削除し、サーバーは停止済み。

## 第2回レビュー指摘への対応（2026-08-12）

- 新規作成・編集ともMarkdown（`.md`）またはテキスト（`.txt`）だけを許可し、インデクサー・ファイルツリーと同じ除外ディレクトリ規則を共有した。
- LLM由来の単独サロゲートを含む内容はUTF-8の置換文字へ正規化し、失敗時の一時ファイル・作成途中のファイルを残さないようにした。
- 原子的置換の前に元ファイルのパーミッションを一時ファイルへ引き継ぐようにした。
- 500の書き込み失敗はスタックトレース付きでアプリケーションログに記録するようにした。
- `implementation_plan.md` の編集対象指定を、実装どおり「プロジェクトフォルダからの相対パス」へ明確化した。
- 隔離環境で、ネスト編集後も755のパーミッションを維持すること、不正Unicodeを置換して204で保存できること、`.git/config` と `run.sh` が400で拒否されること、一時ファイルが残らないことを確認した。検証プロジェクトは削除API経由で削除し、サーバーは停止済み。
