## 指摘事項

### 中1: ファイルツリーが画面内に収まらず、インデックス進捗インジケーターが事実上見えない

**該当箇所**: `src/pages/ProjectChat.tsx:14`（`<div className="flex min-h-full">`）/ `src/components/project/FileTree.tsx:179`

`FileTree` は内部にスクロール領域を持つ設計になっています。

```tsx
<aside className="flex w-72 shrink-0 flex-col border-l bg-card">
  …
  <div className="min-h-0 flex-1 overflow-y-auto py-2">   ← ここでスクロールさせたい
  …
  {indexStatus ? <IndexProgress indexStatus={indexStatus} /> : null}   ← 下端に固定したい
```

しかし親が `min-h-full`（＝`min-height` のみ）で**高さが確定していない**ため、`flex-1 min-h-0` は縮む先を持ちません。結果として `overflow-y-auto` が一度も発動せず、`aside` がコンテンツの高さまで伸びます。

**実測（1000ファイルのプロジェクト / ビューポート高さ 889px）**

```
ファイルツリー aside の高さ : 28,182 px
内部スクロール領域          : clientHeight 28,044 / scrollHeight 28,044
                              → scrollHeight === clientHeight のためスクロールが発生しない
最後のファイル行の下端      : y = 28,081 px
進捗インジケーターの位置    : y = 28,102 px
画面内に見えているか        : false
見るために必要なスクロール量: 27,213 px
```

進捗表示のテキスト（`インデックスの作成に失敗しました` / `100%`）は DOM 上には存在しますが、**1000行のファイル一覧を最後までスクロールしないと到達できません**。`implementation_plan.md` T5-2 の「ツリー下部にインデックス進捗インジケーター」も、`design.md` のレイアウト図でファイルツリー枠の下端に `[index中...]` を置いている意図も、この状態では満たせていません。初回インデックス中こそ見せたい情報が、いちばん見えない場所にあります。

副作用として、中央のチャット領域も一緒に 28,182px まで伸びます。スクリーンショットでは、`items-center justify-center` で縦中央寄せされた案内文が画面外（およそ 14,000px 地点）へ飛び、**中央パネルが真っ白**になりました。T6-3 でここに入力欄とメッセージ一覧が入ると、入力欄が画面外に出る形になります。

ファイル数が少ないうち（13エントリ）は下端に正しく表示され、見た目は設計どおりです。**問題は件数が増えたときだけ**なので、実装時の手元確認では気づきにくい種類の不具合です。

**対応**: `ProjectChat.tsx` の外枠を高さが確定する形にしてください。祖先の `MainPanel` 側は既に `h-screen overflow-hidden` で高さが閉じているので、`min-h-full` を `h-full` に変えて `overflow-hidden` を足すだけで、`aside` 内の `flex-1 min-h-0 overflow-y-auto` が期待どおり働きます。修正後は「1000行でもツリー内だけがスクロールし、進捗が下端に残る」ことを確認してください。

### 中2: ツリーの表示内容がRAGの実際の対象と食い違う（シンボリックリンク）

**該当箇所**: `backend/services/file_tree.py:90-94`

```python
if (
    file_path.suffix.lower() not in SUPPORTED_FILE_SUFFIXES
    or file_path.is_symlink()
):
    continue
```

`T5-2_impl.md` の設計判断には「ファイルツリーはRAG対象を明確にするため、`.md` と `.txt` のみを表示する」「外部を参照しうるシンボリックリンクは表示対象から除外している」とあります。ところが**T5-1 のインデクサーはシンボリックリンクを除外していません**。`find_project_files` は `S_ISREG(file_path.stat().st_mode)` で判定しており、`stat()` はリンクを辿るため、リンク先が通常ファイルなら**インデックス対象になります**。

**実測（同一プロジェクトでの突き合わせ）**

```
配置したもの:
  a.md, docs/b.md, docs/c.txt
  link-internal.md  → プロジェクト内の a.md へのリンク
  link-external.md  → プロジェクト外 (…/t52/outside/external.md) へのリンク
  link-broken.md    → リンク切れ

ファイルツリーAPI が返したファイル:
  a.md, docs/b.md, docs/c.txt            （3件）

T5-1 が実際にインデックスしたファイル:
  a.md, docs/b.md, docs/c.txt,
  link-external.md, link-internal.md      （5件）
```

`link-external.md` は**プロジェクトフォルダ外にある文書の内容がベクトルDBに取り込まれている**にもかかわらず、ファイルツリーには一切現れません。T6-2 でRAG検索が走ればその内容はコンテキストとしてLLMに渡りますが、ユーザーは「RAG対象を明確にする」はずのUIを見ても、外部ファイルが含まれていることに気づけません。

**リンクを隠すという判断自体は妥当な方向です。** 問題は、隠す場所がUI側だけで、実データを作っているインデクサー側が素通しになっていることです。`AGENTS.md` 7章はファイル**書き込み**をプロジェクトフォルダ直下に限定するよう定めており、T6-1でファイル操作を実装する際にも同じ境界の話が出てきます。ここで表示とインデックスの境界定義を揃えておくのが安全です。

なお、リンク切れ（`link-broken.md`）については両者とも除外しており一致しています（T5-1側は警告ログを出してスキップ、ツリー側は非表示）。

**対応（推奨）**: `backend/services/indexer.py` の `find_project_files` にも `file_path.is_symlink()` の除外を入れ、**インデックスとツリーの対象定義を一致させてください**。`EXCLUDED_DIRECTORY_NAMES` / `SUPPORTED_FILE_SUFFIXES` を共有しているのと同じ考え方で、判定条件そのものを `file_tree.py` と共有する形にすると、今後ずれません。逆に「リンクもRAG対象として扱う」と決めるなら、ツリー側の除外を外したうえで `design.md` か `implementation_plan.md` に方針を明記してください（`AGENTS.md` 11章）。

## 軽微な指摘

### 軽微1: 対象ファイルを1つも含まないフォルダもツリーに表示される

**該当箇所**: `backend/services/file_tree.py:32`（`add_directory_nodes` を全走査ディレクトリに対して無条件で呼んでいる）

`T5-2_impl.md` の設計判断は「フォルダはこれらの対象ファイルを含むパスとしてネスト表示する」と書かれていますが、実装は `os.walk` が訪れたすべてのディレクトリをノード化しています。

**実測**

```
📁 proj
  📁 docs
    📄 b.md
    📄 c.txt
  📁 emptydir       ← 空フォルダ。中身なしで表示される
  📁 imagesonly     ← pic.png しかない。中身なしで表示される
  📄 a.md
```

`emptydir` も `imagesonly` も、RAGの対象を1つも含みません。実際のノートフォルダは画像や添付ファイル専用のディレクトリを持つことが多いので、ツリーが「開いても何も入っていないフォルダ」で埋まります。ドキュメントの記述と実装のどちらかに寄せてください（葉から刈り込むなら `sort_tree` と同じ再帰で空ディレクトリを落とせます）。

### 軽微2: ポーリング失敗のエラー表示が、バックエンド復旧後も消えない

**該当箇所**: `src/components/project/FileTree.tsx:133-149`

`loadTree` は成功時に `setError(null)` していますが、`loadIndexStatus` にはそれがありません。ツリーは初回1回しか取得しないため、**ポーリングが一度でも失敗すると、そのエラー表示はアンマウントまで残り続けます**。

**実測**

```
1. 正常表示（ツリー3ファイル + 進捗インジケーター）
2. バックエンド停止 → 3秒後: 「サーバーに接続できません」が表示される（正しい）
3. バックエンド再起動 → 6秒後:
     進捗ラベル : 「インデックスの作成に失敗しました」← ポーリングは成功して更新されている
     エラー表示 : 「サーバーに接続できません」        ← 残ったまま
```

ポーリング自体は復旧しており内容も更新されているのに、上部には接続エラーが出続けます。`loadIndexStatus` の成功時にも `setError(null)` を入れれば解消します。

## 任意（対応しなくてもマージ可）

1. **`done` / `error` に到達してもポーリングが止まらない** — 実測で7秒間に4リクエスト。終端状態でも2秒ごとに投げ続けます。ローカル通信なので実害は小さいですが、`done` になったら `clearInterval` する（あるいは `error` は間隔を空ける）と素直です。

2. **ファイルツリーは初回のみ取得され、更新されない** — インデックスが完了してもファイルを追加してもツリーは変わりません。`indexStatus` が `indexing` → `done` に変化したタイミングで再取得すると、初回インデックス直後の表示が自然になります。

3. **読めないサブディレクトリを無言で除外する** — `build_file_tree` の `os.walk` に `onerror` がないため、権限のないディレクトリは例外もログもなく消えます（実測: `chmod 000` のフォルダを置いても HTTP 200、ログ出力なし）。読み取り専用のAPIなので破壊的な影響はなく、T5-1 側も同じフォルダをスキップするので結果は一致しますが、T5-1 が警告ログ + `error` ステータスを出すのに対しツリーは完全に無言、という非対称は残ります。`api/projects.py` の `except OSError → 500` も、この経路では発火しません。

4. **エラー時に進捗バーが満タンになる** — `error / 100` のとき、赤いラベルの下でバーが100%まで塗られます（実測のスクリーンショットで確認）。T5-1 のレビューで申し送った「`error` は全体失敗と一部スキップ完走の両方で返る」という仕様に由来します。ステータス文言が主なので実害はありませんが、エラー時はバーを描画しないか色を変えると誤解が減ります。

差分: `src/pages/ProjectChat.tsx`（外枠を `h-full overflow-hidden` へ）、`backend/services/indexer.py`（`is_supported_project_file` の追加）、`backend/services/file_tree.py`（共有判定＋空ディレクトリの刈り込み）、`src/components/project/FileTree.tsx`（エラー解除とポーリング停止）

## 判定

**要修正**

第1回の指摘4件はすべて解消しました。特に中2の直し方は良く、判定関数 `is_supported_project_file()` をインデクサーとファイルツリーで共有する形にしたため、**今後この2つがずれません**。中1も1000ファイルで完全に意図どおりの表示になりました。

一方、軽微2（ポーリング失敗のエラーが消えない）の修正が**新しい欠陥を生んでいます**。`loadIndexStatus` の成功時に `setError(null)` を無条件で呼ぶようになったため、**ファイルツリーの取得に失敗したことが進捗ポーリングの成功によって揉み消され、パネルが「読み込み中...」のまま永久に固まります**。バックエンド（Tauriサイドカー）の起動が間に合わないアプリ起動直後に、そのまま踏みます。

## 新規指摘

### 中1: ツリー取得の失敗が進捗ポーリングの成功に打ち消され、「読み込み中...」で固まる

**該当箇所**: `src/components/project/FileTree.tsx:139`

```ts
async function loadIndexStatus(): Promise<void> {
  try {
    const result = await getProjectIndexStatus(projectId);
    if (isActive) {
      setIndexStatus(result);
      setError(null);          // ← ツリー取得のエラーまで消してしまう
```

`error` state を `loadTree` と `loadIndexStatus` が共有しているため、**別々の原因のエラーが互いに干渉します**。ツリーは初回1回しか取得しないので、一度消されたエラーは二度と戻りません。

**実測（バックエンドが落ちている状態でプロジェクトチャットを開き、その後バックエンドを復旧）**

```
1. バックエンド停止 → /projects/{id} を開く
     loadTree        : 失敗 → error に「サーバーに接続できません」
     loadIndexStatus : 失敗 → 同上
2. バックエンド起動（約12秒後）
     loadIndexStatus : 成功 → setError(null) でエラーを消去、status が done のためポーリング停止
     loadTree        : 再試行されない

5秒後のファイルツリーパネル:
  表示テキスト      : ["読み込み中..."]
  ツリー行数        : 0
  進捗ラベル        : null
  index-status 要求 : 10回（復旧後に成功して停止）
  files 要求        : 3回（すべて失敗したまま）
```

エラー表示もなく、ツリーも出ず、**「読み込み中...」だけが永久に残ります**。ユーザーから見ると原因不明のまま右サイドバーが死んだ状態です。復帰させるには別画面へ移動して戻る（＝アンマウント）しかありません。

これは**現実的なタイミングで踏みます**。`design.md` のとおり FastAPI は Tauri のサイドカーとして起動されるため、アプリ起動直後はバックエンドがまだ立ち上がっていません。その状態でプロジェクトチャット画面を開けば、この経路にそのまま入ります。

なお、**同じ「フォルダが見つからない」でも順序次第で表示が変わります**。プロジェクトフォルダをリネームした状態で開いた場合は、`files` が404を返すのが `index-status` の成功より遅いため、エラーが正しく残りました。

```
（フォルダをリネームして開いたケース）
  0.6秒後 / 2.6秒後 / 6.6秒後 いずれも:
  「プロジェクトフォルダが見つかりません: …」を表示   ← こちらは正しい
```

つまり**どちらのメッセージが残るかがレースで決まる**状態です。第1回で指摘した「エラーが消えない」の逆側に振れてしまいました。

**対応（推奨）**: `error` state を用途ごとに分けてください。

```ts
const [treeError, setTreeError] = useState<string | null>(null);
const [statusError, setStatusError] = useState<string | null>(null);
```

`loadTree` は `treeError` のみ、`loadIndexStatus` は `statusError` のみを操作すれば、互いに干渉しません。表示は両方を出すか、`treeError ?? statusError` のように優先順位を決めれば十分です。

あわせて、**接続が復旧したら `loadTree` も再試行する**と、この状態からユーザー操作なしで復帰できます（第1回の任意2「ツリーが初回のみ取得され更新されない」も同時に解消します）。
