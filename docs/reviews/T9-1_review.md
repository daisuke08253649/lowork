## 要修正

### 要修正1: 初期選択モデルが一覧の先頭固定で、初回送信がほぼ必ず失敗する

`src/pages/NormalChat.tsx:30` と `src/pages/ProjectChat.tsx:59` は `setModel(response.models[0] ?? null)` で先頭を選ぶ。`GET /ollama/models`（`backend/api/ollama.py`）はOllamaの `/api/tags` をそのまま返すため、**Embedding専用モデルもチャット用モデルとして並ぶ**。この環境では先頭が `nomic-embed-text:latest` だった。

実測（アプリ起動直後、何も操作せずに送信）:

```
"nomic-embed-text:latest" does not support chat
```

「チャットエラー」の本文に上流Ollamaの英語メッセージがそのまま出る。`requirements.md` 6章「UI言語: 日本語固定」「Ollamaが起動していない場合はUI上にわかりやすいエラーを表示する」の趣旨に反する。

さらに悪いことに、検証で `smollm2:135m` をDLした後は**そちらが先頭**になった。この状態でプロジェクトチャットを送ると、135Mのモデルは指定JSONを守れず「Ollamaから有効な応答を取得できませんでした。」が返る（実測）。**設定画面で小さいモデルを試しにDLすると、以後の既定モデルがそれに変わる**という導線になっている。

対応案（いずれか、または組み合わせ）:

1. `backend/api/ollama.py` の `OllamaModel`（32行目）に `capabilities: list[str] = []` を追加し、`completion` を持つモデルだけを `/ollama/models` で返す。Ollamaの `/api/tags` は既に `"capabilities":["embedding"]` / `["completion","tools","thinking"]` を返しているので追加通信は不要
2. 選択したモデル名を `localStorage` に保存し、次回以降はそれを初期値にする（要修正2と同時に解決できる）
3. `backend/api/chat.py:205,401` の 502 パススルー（上流の英語メッセージ）に、日本語のフォールバック文言を用意する

### 要修正2: 画面を移動するたびにモデル選択がリセットされる

`model` は `NormalChat` / `ProjectChat` の `useState` なので、設定画面やプロジェクト一覧を経由して戻るとアンマウントで捨てられ、再び `models[0]` に戻る。

実測: `gemma4:12b` を選んで会話 → 設定画面へ移動 → チャットへ戻ると `nomic-embed-text:latest` に戻っていた。履歴からの会話復元後も同じ。要修正1と重なると「毎回選び直さないと必ず失敗する」状態になる。

実行モード（確認/自走）は `design.md` 8章の決定どおり `localStorage` に永続しているので、**モデル選択だけが揃っていない**。同じ方式で永続させるのが自然。

### 要修正3: プロジェクトフォルダが失われても、古いインデックスのまま黙って回答し続ける

プロジェクトフォルダをリネーム（＝ユーザーがフォルダを移動・削除した状況）してから `/project-chat` を叩くと、**200が返り、消えたはずのファイル内容で回答し、会話も保存される**。

実測:

```
（project フォルダをリネームした状態で）
Q: コーヒーのメモに書いてある湯の量は何mlですか。
A: コーヒーのメモ（coffee.md）に記載されている湯の量は300mlです。   ← 200 OK、会話も保存
```

原因は `backend/services/indexer.py:133` の `except Exception:` が例外を内部で握りつぶすこと。`backend/api/chat.py:439` は `await index_project(...)` を try で囲んで「プロジェクトのインデックス更新に失敗しました」(500) を返す作りだが、**例外が上がってこないのでこの分岐に到達しない**。その後の `search()` は残っているChromaコレクションを引けてしまうため、古いスナップショットで回答が成立する。

ユーザーが気づける手掛かりは、ファイルツリー側の404表示（「プロジェクトフォルダが見つかりません: ...」）とインデックス失敗バーだけで、チャットの回答自体には何も出ない。

対応案: `index_project` に「呼び出し元へ失敗を伝える」経路を用意する（戻り値、または `/project-chat` からは例外を投げるラッパーを使う）。最低限、`get_index_status` が `error` のときはチャット側にも警告を出したい。

## 軽微

1. **見えない会話が増え続ける**: プロジェクト画面を離れて戻ると `conversationId` がリセットされるため、次の送信で毎回新しい会話が作られる。UIから一覧できないので、DBにだけ会話が溜まる（実測: 同一プロジェクトで3会話）。差分1とセットで対応するのが自然
2. **タイトル自動生成に検証がない**: `backend/services/chat_history.py:214` は応答の先頭行20文字をそのままタイトルにする。非力なモデルではプロンプトのエコーがそのまま入る（実測: `ユーザー: こんにちは？`、`以下の文字幕を、20篇日本語タイトルに秘`）。「ユーザー:」始まりや、生成に失敗した形跡がある場合は既定タイトルのままにするなどの簡単なガードが欲しい
3. **自走モードでの既存ファイル編集は破壊的**: 編集は全文置換で、バックアップも取り消しもない。今回の実測でも `gemma4:12b` が「心配な」を40回以上繰り返す壊れた本文を返した。確認モードのプレビューで気づけたが、**自走モードなら既存メモが丸ごとこの内容で上書きされていた**。MVPでこのままにするなら、せめて自走モードのトグルに「既存ファイルも即上書きされる」旨の注意書きを添えたい
4. **シンボリックリンク経由の編集拒否メッセージが実態と合わない**: `.md` のリンクを編集しようとすると「Markdownまたはテキストファイルを指定してください」が返る（`backend/services/file_ops.py:83` の `validate_supported_file` が `is_symlink()` も見ているため）。**ブロック自体は正しい**が、理由が伝わらない
5. **想定外エラーの文言が英語のまま出る**: `getProjectErrorMessage` は最後に `error.message` へフォールバックする。Chrome検証時の実測では「Cannot read properties of undefined (reading 'invoke')」がそのままAlertに出た（この事象自体はTauri外での実行によるものだが、未知の例外では実機でも同じ経路を通る）
6. **初回応答までが無言で長い**: モデルのロードを含めて最初のトークンまで約34秒、その間の表示は「応答を生成中...」のみ（gemma4:12b、実測）。プロジェクトチャットは再インデックス＋RAG検索が前段に入るぶんさらに長く、200ファイルのプロジェクトで30〜60秒かかった。MVPでは許容範囲だが、初回起動時のモデルロードだけでも一言添えると体感が変わる

### 要修正

#### 要修正1: プロジェクト会話一覧が送信後に更新されない

`src/components/layout/Sidebar.tsx:62` の `useEffect` は依存配列が `[projectId]` だけなので、**そのプロジェクト画面にいる間は一覧を取り直さない**。通常チャットは送信完了時に `loadChatConversations(true)` が走り、さらにタイトル生成のポーリング（`useChat.ts` の `waitForGeneratedTitle`）まであるのとは対照的。

実測（プロジェクト画面で1往復送信し、応答が完了した直後）:

```
サイドバー   : 「履歴はまだありません」
DB          : 会話1件・メッセージ2件
API         : GET /chat/conversations?project_id=... → 1件返る
```

タイトルが生成されて `コーヒーの湯量の確認` になった後も表示は変わらず、プロジェクト一覧を経由して入り直すと初めて出てくる。**会話しているのに「履歴はまだありません」**と出るので、保存されていないと誤解する。

対応案: 送信完了後（`ProjectChat` の `handleSubmit` 成功時）に一覧を再取得する。通常チャットと同じくタイトル生成待ちのポーリングも入れると挙動が揃う。

#### 要修正2: プロジェクト会話一覧の取得失敗が握りつぶされ、未処理のPromise拒否になる

5. **取得失敗の表示がバックエンド復帰後も自動では消えない**: Ollama警告バナーだけは自動で復帰するため、**バナーが消えたのに履歴・ファイルツリー・モデル一覧の3か所がエラーのまま**という状態になる（実測）。画面を出入りすれば復旧するので実害は小さく、ファイルツリーとモデル一覧は既存の挙動。バナーの「Ollamaを起動すると自動的に再接続します。」という文言との落差だけ気になる
6. **タイトル生成ポーリング中のリクエストが2倍になっている**: `pollGeneratedProjectTitle`（`useChat.ts:152`）が毎tickで `getChatConversations` を呼び、さらに `refreshProjectHistory()` でサイドバーにも同じ取得をさせるため、1tickあたり2リクエスト。実測で送信からタイトル反映までに `GET /chat/conversations?project_id=...` が9回。ローカルなので実害はないが、タイトル生成に失敗して24回回り切ると48リクエストになる
7. **プロジェクト画面を直接URLで開くと見出しが「プロジェクト」のまま**: `ProjectChat` はプロジェクト名を `projectStore` からのみ引くので、一覧を経由せずに開くと名前が出ない（ファイルツリーには正しくフォルダ名が出る）。Tauriでは通常 `/` から始まるため、⌘Rでのリロード時くらいしか踏まないが、URL復元を前提にした今回の機能とは相性が悪い

> いずれも「動作が壊れている」ものではないため、T9-1の完了とマージは止めない。4は小さい修正で直るので、余力があれば拾いたい。

### 軽微

#### 軽微1（新規）: タイトル更新の24回上限が二度と復活せず、サイドバーのタイトルが古いまま固定される

`Sidebar.tsx:80-88` は、`projectId` が変わったときだけ `titleRefreshAttemptsRef` を0に戻す。ところが `!projectId`（プロジェクト一覧・通常チャット・設定）のときは **`titleRefreshProjectIdRef` を触らずに早期リターン**するため、SPA内で「プロジェクトを離れて同じプロジェクトに戻る」をしても判定が `false` のままで、**回数がリセットされない**。

一度でも「タイトルが永久に付かない会話」（下記 軽微2 が原因で発生する）が一覧に残ると、`hasUntitledConversation` が常に `true` になり、24回を使い切った後はそのプロジェクトのタイトル更新が**セッション中ずっと止まる**。

実測（バックエンドのアクセスログとDOMを突き合わせ）:

```
上限を使い切った後、SPAで「プロジェクト」→ 同じプロジェクトへ戻る
  → GET /chat/conversations?project_id=… は 79秒で 1回（マウント時の1回だけ。ポーリング再開なし）

その状態で新しい会話を1件送信し、タイトル生成の完了を待つ:
  API      : ["紅茶の適切な蒸らし時間", "recovery-i.mdの新規作成", "新しいチャット", …]
  サイドバー: ["新しいチャット",        "recovery-i.mdの新規作成", "新しいチャット", …]
                ↑ 生成済みのタイトルが110秒以上たっても反映されない
```

送信のたびに1回だけ再取得は走るが、タイトル生成に45〜100秒かかるため**その1回には間に合わず**、結局リロードするまで「新しいチャット」のままになる。データは壊れない（DBには正しいタイトルが入っている）ので軽微だが、「タイトルが付かないのが普通」に見えてしまう。

対応案: `!projectId` の早期リターンの前に `titleRefreshProjectIdRef.current = undefined` を入れる（プロジェクトを離れたら次回の入り直しでリセット）。あわせて「上限に達したのは、生成に失敗し続けている会話が1件あるからで、新しく作った会話には別枠の予算を与えたい」と考えるなら、上限を「会話一覧全体」ではなく「未タイトルの会話IDの集合が変わったらリセット」に変えるほうが素直。

#### 軽微2（新規）: Ollamaがタイトルを空で返すと `IndexError` になり、トレースバックがログに出る

`chat_history.py:216`:

```python
title = response.json()["message"]["content"].strip().splitlines()[0][:20]
```

`content` が空文字（または空白のみ）だと `.splitlines()` が `[]` を返し、`[0]` で `IndexError` になる。`except` 節に `IndexError` が含まれているので**アプリは落ちない**が、`logger.warning(..., exc_info=True)` によってトレースバック全体がログに出る。今回の検証で1回発生した（`t9e/logs/be.log`。バックエンドの想定外例外はこの1件のみ）:

```
IndexError: list index out of range
  File "backend/services/chat_history.py", line 216, in generate_conversation_title
```

このとき会話は「新しいチャット」のまま恒久的に残り、それが 軽微1 の引き金になる。

対応案: `lines = content.strip().splitlines()` を取ってから `title = lines[0][:20] if lines else ""` とし、空なら `is_valid_conversation_title("")` が `False` を返して静かに諦める（`IndexError` を例外処理に頼らない）。

#### 軽微3（新規・UX）: チャット削除に確認ダイアログがない

プロジェクト削除には `AlertDialog`（`ProjectList.tsx:169-187`「この操作は元に戻せません」）があるのに、チャット会話の削除（`Sidebar.tsx:250`）は**ゴミ箱アイコンのワンクリックで即座に確定**する。会話行の右端（x=203）とゴミ箱ボタンの左端（x=207）が4pxしか離れておらず、会話を開こうとして押し間違えると復旧できない。

`design.md` に確認ダイアログの指定はないので設計逸脱ではないが、削除系の挙動が2箇所で食い違っているのは気になる。MVP後でよい。

#### 軽微4（第4回から継続・未対応）: エラー表示と古い一覧が同時に出る

#### ファイル操作の防御（詳細）

`POST /files/apply` に直接投げた結果。プロジェクト外に置いたカナリアファイルは最後まで `ORIGINAL` のまま。

| # | action | filename | 結果 |
|---|---|---|---|
| 1 | create | `../escape.md` | 400 プロジェクトフォルダ内の安全なパスを指定してください |
| 2 | create | `sub/nested2.md` | 400 新規ファイルはプロジェクトフォルダ直下の名前で指定してください |
| 3 | edit | `sub/nested.md` | 204（プロジェクト配下の既存ファイル編集は仕様どおり許可） |
| 4 | create | `/tmp/evil.md` | 400 安全なパス |

防御が効いている理由も確認した:

- `is_supported_project_file()`（`indexer.py`）が `not file_path.is_symlink()` を含むので、**createもeditもシンボリックリンクを弾く**
- `create_file()` は `open("x")`＝`O_CREAT|O_EXCL` なので、壊れたシンボリックリンク越しの作成もOS側で失敗する
- `get_existing_target_path()` は `is_symlink()` に加えて `resolve().is_relative_to(project_path)` を見るので、親ディレクトリがシンボリックリンクのケースも塞がっている
